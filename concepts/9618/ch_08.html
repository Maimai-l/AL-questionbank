8.1文件系统与关系数据库

文件系统里每个程序各存一份数据,会重复、会不一致;关系数据库把数据存在互相链接的表里,每个数据只存一次。

文件系统(file-based approach)里,每个程序按自己写定的记录结构读写文件,一个程序改了结构,另一个就得重写。它有三个局限:数据重复占空间,被不同应用分别改动后变得不一致,查询受数据结构和所用软件限制。数据冗余data redundancy是同一数据不必要地存在多处(unnecessary repetition of the same data stored in more than one place);数据不一致data inconsistency是同一数据在不同地方存得不同,因为副本没有全部更新(copies are not all updated)。

关系数据库relational database把数据组织成表,表里的数据项靠主键和外键建立的关系链接(data items are linked by relationships between primary and foreign keys)。数据只存一次,各应用共用,所以冗余少、数据一致(data is consistent),数据也不再依赖具体的程序,这叫程序与数据独立program-data independence(data is independent of the program processing it)。

常考比较文件系统与关系数据库

文件系统关系数据库
重复:数据被各应用重复存放,浪费空间(data items duplicated; storage space wasted)重复:每个数据只存一次,冗余很少(reduced data redundancy // less repeated data)
修改:一个应用改了,另一个没改,数据不一致(more data inconsistency // worse data integrity)修改:一处修改,所有应用都看到,数据一致(reduces data inconsistency // improves data integrity)
独立性:查询取决于数据结构和软件,数据不独立(data is not independent)独立性:查询不依赖数据结构和软件,数据独立(data is independent)
了解文件系统的问题从哪来

教材的例子:公司的工资文件和销售文件各由一个程序使用。员工名字和员工编号在两个文件里各存一份,存法还不一样;员工编号在工资记录里是第 5 个字段,在销售记录里是第 2 个字段。如果工资程序改了编号而销售程序没改,同一个员工就有两个不同的编号(these fields may contain different values for the same member of staff)。

8.1表里的术语

一张表对应一种实体:每一行是这个实体的一个实例,每一列是它的一项属性。

一张表(table: a group of similar data, with rows for each instance of an entity and columns for each attribute)存一种实体entity的数据,实体是任何可以存数据的对象(anything that data can be stored about)。表中一行是实体的一个实例(one instance of an entity),叫元组tuple,也叫记录record。一列是实体的一项数据(an individual data item stored about an entity),叫属性attribute,也叫字段field(a column/attribute in a table)。

必考分清实体、属性、元组

术语评分细则式说法
entityan object about which data can be stored // anything that data can be stored about
attributean individual data item stored about an entity // a column/attribute in a table
tupleone instance of an entity // an object that data is stored about, shown as a row
了解索引:让查找更快

索引index是用表中一列或几列建立的数据结构,用来加快查找(a data structure built from one or more columns to speed up searching for data)。例如给 Student 表按 Class、Second Name、First Name 建索引,就能很快得到按姓排序的班级名单。

8.1键

主键唯一标识一行;外键是本表里的一个字段,指向另一张表的主键,表与表就是靠它链接起来。

候选键candidate key是表中值不会重复的属性或最小的属性组合(an attribute or smallest set of attributes where no tuple has the same value)。从候选键里选一个作主键primary key,它唯一标识表里的每条记录(the unique attribute / combination of attributes used to identify the record / tuple)。没被选作主键的候选键叫次键secondary key(a candidate key that has not been chosen as a primary key)。外键foreign key是一张表里的字段,链接到另一张表的主键(a field in one table that is linked to a primary key in another table)。

必考认出各种键

键怎么认(以元素表为例)
候选键值不重复的属性:Symbol、Name、Atomic Weight
主键从候选键里选的那一个:Symbol
次键没被选中的候选键:Name、Atomic Weight(an additional/alternative key used as well as the primary key to locate specific data)
外键本表字段,在另一张表里是主键:STUDENT 表的 ClassID
了解主键怎么选

大多数表只有一个候选键,它就是主键。名字可能重复,所以学生表另加一个对每个学生都唯一的 StudentID 当主键;教师表同理,教材建议用教师执照号 LicenceNumber 当主键,因为教师姓名不一定唯一(teacher names might not be unique)。

8.1关系与参照完整性

一张表的外键指向另一张表的主键,就形成一个关系;外键的值必须在主键里找得到。

一张表有外键指向另一张表的主键,两张表之间就有了一个关系(a relationship: one table has a foreign key that refers to a primary key in another table)。参照完整性referential integrity保证每个外键值都有对应的主键值(every foreign key has a corresponding primary key),不存在的数据不能被引用(data that does not exist cannot be referenced);一处数据改了,所有相关记录跟着改(cascading update/delete)。例如 STUDENT 表里的 ClassID 只能取 CLASS 表里已有的值。

两张表之间的关系有四种:一对一 1:1、一对多 1:m、多对一 m:1、多对多多对多关系many-to-many relationshipm:m。多对多不能直接用外键表示,要用一张连接表linking table拆成两个一对多(removing the many-to-many relationship by creating a linking table)。

常考判断关系类型

类型怎么看例
一对多 1:m一边的一行对应另一边多行one staff member can have many devices
多对一 m:1倒过来看同一个关系many performances of each show
多对多 m:m两边的一行都可以对应对方多行Owner and Tree
一对一 1:1两边各对应一行each employee has one desk

STUDENT 和 CLASS 是多对一:同一个 ClassID 在 Student 表里出现很多次,在 Class 表里只出现一次。

了解怎么拆多对多关系
新建一张连接表,起一个合适的名字a linking table with an appropriate name
→
放进两边的主键,各作外键the primary keys of both tables as foreign keys
→
两个外键组合作主键,或新增一个命名的主键(composite) primary key // a named new primary key

8.1E-R 图

E-R 图用方框画实体,用连线画关系,线的两端标出是 1 还是 m。

E-R 图E-R diagram是数据库和实体之间关系的图形表示(a graphical representation of a database and the relationships between the entities),用来记录数据库的设计。逻辑模式常用 E-R 图来展示数据库的结构和关系(uses methods such as an E-R diagram to show the structure of the database and its relationships)。

了解关系是必须的还是可选的

关系还分必须和可选(mandatory or optional):办公室里每个员工有一张桌子,但可以有空桌子,所以桌子和员工的关系是 0 或 1,可选;每位母亲至少有一个孩子,所以母亲和孩子的关系是 1 或多,必须。关系的类型再加上必须还是可选,合起来叫关系的基数(cardinality)。

8.1规范化

规范化把一张大表拆成几张相关的小表,让同一个数据只存一处;一共三步:去掉重复组、去掉部分依赖、去掉非键依赖。

规范化normalisation是把数据整理进两张或更多相关的表,使数据冗余最少(organising data into two or more related tables so that data redundancy is minimised)。第一范式first normal form (1NF)要求没有重复的属性组,数据都是原子的(no repeating groups of attributes // data is atomic)。第二范式second normal form (2NF)在 1NF 之上,所有属性完全依赖整个主键(all attributes must be fully dependent on the (composite) primary key),不存在部分依赖partial dependency(no partial dependencies)。第三范式third normal form (3NF)在 2NF 之上,所有属性只依赖主键,不依赖别的属性(all attributes must be fully dependent on the primary key and no other attributes),即没有非键依赖non-key dependency(no non-key dependencies // no transitive dependencies)。

常考判断一张表在第几范式

看到违反怎么改
一格里有多个值,或有重复的属性1NF重复的部分移到新表,用外键连回来
复合主键,某属性只依赖主键的一部分2NF该属性连同那部分主键拆成新表
某属性由另一个非键属性决定3NF两者一起拆成新表,决定者当新表主键
了解为什么要规范化

不规范的表更大,数据越多越难更新,也越难查询(harder to update the database when changes are made and more difficult to extract the required data)。教材把学生、班级、教师放在一张表里,会出现三种麻烦:每加一个学生,就要重复写教师的姓名、地址、执照号和教室;教师换人,所有含他的记录都要改;一个班的学生全走了,这个班的信息也就丢了。

8.1规范化的例子

教材用 School 数据库一步步规范化:先拆出学生的科目,再拆出科目的教师,最后拆出班级和教师,共五张表。

学生的科目和科目教师是重复属性,先移到新表 STUDENTSUBJECT,它的主键是由 StudentID 和 SubjectName 两个属性组成的复合主键composite key(a composite key formed from two attributes),其中 StudentID 同时是指向 STUDENT 的外键。

必考把表规范化

步骤发现问题 → 做法
1NFSubjectName, SubjectTeacher 是重复属性(repeating attributes)
→ 移到新表 STUDENTSUBJECT,用外键 StudentID 连回 STUDENT 表
2NFSubjectTeacher 只依赖复合主键里的 SubjectName(partial dependency)
→ 新建 SUBJECT 表,放 SubjectName 和 SubjectTeacher
3NFLocation 和 TeacherName 依赖 ClassID;
LicenceNumber、Address 和 TeacherDateOfBirth 依赖 TeacherName(non-key dependencies)
→ 拆出 CLASS 和 TEACHER 两张表;教师姓名可能重名,改用 LicenceNumber 当主键
了解每一步之后的表

开始时:STUDENT(StudentID, FirstName, SecondName, DateOfBirth, SubjectName, SubjectTeacher, ClassID, Location, TeacherName, LicenceNumber, Address, TeacherDateOfBirth),科目和科目教师重复了几组。

1NF:STUDENT 去掉科目;STUDENTSUBJECT(StudentID, SubjectName, SubjectTeacher)。

2NF:STUDENTSUBJECT(StudentID, SubjectName);SUBJECT(SubjectName, SubjectTeacher)。

3NF:STUDENT 去掉教师和教室的信息,新增 CLASS 和 TEACHER,SUBJECT 里的教师改记 LicenceNumber。教材的练习还提示:一门科目可能有多位教师,这张 SUBJECT 表还可以再改进。

8.2DBMS 弥补了文件系统的什么

DBMS 站在应用程序和数据库之间,统一管理数据的创建、存储、修改和删除,解决冗余、不一致和数据依赖三个问题。

数据库管理系统database management system (DBMS)是用来定义、创建和操作数据库的系统软件(systems software for the definition, creation and manipulation of a database)。它按已定义的数据结构建库,新数据的录入、存储、修改和删除都由它管理(data management: the organisation and maintenance of data in a database)。

常考DBMS 如何解决文件系统的局限

局限DBMS 怎么解决
冗余数据放在分开但相互链接的表里,大多数数据只存一次(reduced data redundancy // less repeated data);用来链接的外键值会重复,删除它们时 DBMS 会报错提醒
不一致数据只存一处,更新一次所有应用都看到(data consistency is maintained // data integrity is improved)
数据依赖数据结构的改变由 DBMS 处理,对应用几乎没有影响(changes to the data structure are managed by the DBMS);每个应用只能访问它需要的字段和表

8.2数据字典、逻辑模式与访问权限

数据字典记录关于数据的数据,逻辑模式是不依赖具体 DBMS 的设计图,访问权限规定谁能对数据做什么。

数据字典data dictionary是一组存放数据库元数据metadata的数据(data about the data in the database),例如表名、字段名、数据类型、主键和外键、表之间的关系、验证规则。它帮助保证数据准确、完整、一致。数据建模data modelling是分析并定义数据库需要的数据结构,得出数据模型(to produce a data model);逻辑模式logical schema就是某个具体数据库的数据模型,与建库用的 DBMS 无关(a model of a database that is not specific to one DBMS)。访问权限access rights是授予用户访问、修改或删除数据的许可(permissions to access, modify or delete data)。

常考数据字典与逻辑模式的区别

数据字典逻辑模式
是什么:data about the data in the database // metadata是什么:platform / database independent overview of the database
例子:field names, table name, validation rules, data types, keys, relationships例子:design of entities // E-R diagram

答数据字典时不要只写 metadata 了事:评分细则不接受用 metadata 代替 data dictionary(do not accept metadata as an example or instead of data dictionary)。

常考DBMS 的数据安全措施
用户名和密码usernames and passwords
+
访问权限read/write/delete, read only, append only; views for different users
+
自动定期备份automatic regular back-ups
+
数据加密encryption of the data stored
+
审计跟踪audit trail / activity log of user actions

访问权限既可以限制用户能做的操作,也可以限制能看到的部分:给不同用户不同的视图(views of the data),只让部分用户访问某些表。

8.2DBMS 的工具

开发者在开发者界面里写 SQL,查询处理器负责解释并执行它。

开发者界面developer interface让开发者有命令可以定义、创建和操作数据库(a software tool that allows the user to create items such as tables, forms and reports),可以直接写 SQL 查询,构造更复杂的查询。查询处理器query processor处理并执行用 SQL 写的查询(processes and executes queries written in SQL),让用户能搜索到指定的数据(allows a user to perform searches to find specific data)。

了解查询处理器里面有什么

它包含 DDL 解释器(DDL interpreter)、DML 编译器(DML compiler)和查询执行引擎(query evaluation engine)。DDL 语句被解释后记录在数据字典中;DML 语句被编译成低级指令,由查询执行引擎执行,DML 编译器还会优化这个查询(the DML compiler will also optimise the query)。

8.3SQL 与 DDL:建表和改表

DDL 管数据库的结构:建表、改表、设主键和外键;它和 DML 都是用 SQL 写的。

SQL是关系数据库使用的标准查询语言,既用来定义数据也用来操作数据(structured query language: the standard query language)。DDLdata definition language用来创建、修改和删除构成数据库的数据结构(used to create, modify and remove the data structures that form a database),处理的是数据库的结构,不是表里的数据。

DMLdata manipulation language用来添加、修改、删除和取出关系数据库中的数据(used to add, modify, delete and retrieve the data stored in a relational database)。DDL 处理数据库的结构,DML 处理结构里存的数据。

8.3统计与分组

COUNT、SUM、AVG 对一列做统计;加上 GROUP BY,就按某个字段分组,每组出一行结果。

必考COUNT、SUM、AVG

函数作用
COUNTcounts the number of rows where the column is not NULL
SUMreturns the sum of all the values in the column
AVGreturns the average value for a column with a numeric data type

数个数要用 COUNT,不是 SUM(SUM should be COUNT)。

常考GROUP BY 分组

SELECT 分组字段, COUNT(字段) FROM 表 GROUP BY 分组字段;SELECT PlayerID, COUNT(EventID) FROM EVENT GROUP BY PlayerID;

GROUP BY 把数据排成组(arranges data into groups)。评分点有三个:从表中选出分组字段,对某个字段计数,再按这个字段分组(selecting PlayerID from EVENT; counting EventID; grouping by the PlayerID)。

常考连接加分组的完整例子

每部演出有多少场:

SELECTSHOW.Title, COUNT(PERFORMANCE.PerformanceID) AS NumberOfShowings
FROMPERFORMANCEINNER JOINSHOW
ONPERFORMANCE.ShowID = SHOW.ShowID
GROUP BYSHOW.Title;

先连接两张表,再按演出名称分组,每组数一数有多少场。
