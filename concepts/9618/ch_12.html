12.1程序开发生命周期

开发一个程序要经过分析、设计、编码、测试、维护五个阶段;维护不是终点,程序用多久,这个循环就转多久。

程序开发生命周期program development lifecycle把开发分成五个阶段(five stages: analysis, design, coding, testing and maintenance),让开发有条理、文档清楚,别的开发者也看得懂(well ordered and clearly documented, so that it can be understood and used by other developers)。叫"循环",是因为程序随时可能因新情况或新错误而修改,直到不再使用为止(continues until the program is no longer used)。

分析阶段analysis先调查问题,得出程序要做什么的规格说明(a specification of what the program is required to do),常从可行性研究开始(feasibility study)。结果写成需求规格说明requirements specification,让所有人都明白要做什么(everyone working on the solution understands what is needed)。

设计阶段design用分析阶段的规格说明,说明程序该怎么开发(uses the program specification to show how the program should be developed):有哪些任务、每个任务怎么做、任务怎样配合,用结构图、状态转换图和伪代码记录(structure charts, state-transition diagrams and pseudocode)。

编码coding是用合适的编程语言写出程序(the writing of the program or suite of programs)。测试testing用多组测试数据反复运行程序,保证它在所有条件下都能工作(works under all conditions)。维护maintenance保证程序在使用期间一直正常工作(continues to work during use)。

常考判断活动属于哪个阶段

阶段这个阶段做什么真题里的活动
分析弄清要做什么找客户了解现有系统的问题(the client is interviewed about problems with the current system);程序员确定客户的要求(the programmer identifies the customer's requirements)
设计定下怎么做画结构图(a structure chart is produced);做标识符表(an identifier table is produced);定义记录和文件结构(records and file structures are defined)
编码用语言写出来用编程语言实现算法(an algorithm is implemented in a programming language);可能出现语法错误(syntax errors can occur);IDE 的自动补全(context-sensitive help such as auto-complete)
测试检查对不对用走查法(the walkthrough method is used);做跟踪表(a trace table is produced)
维护投入使用之后的修改修改程序,让它在新硬件上运行(the program is modified to run on new hardware)
了解分析阶段还做哪些事

了解设计阶段还做哪些事

12.1三种开发模型

瀑布模型做完一个阶段再做下一个;迭代模型一轮一轮把系统做大;快速应用开发分几块同时做,先拿原型给客户看。

瀑布模型waterfall model是线性的,上一阶段完成并确认,才开始下一阶段(each stage is completed before the next is begun);每个阶段都有完整文档,客户只在开头和结尾参与(low customer involvement; only involved at the start and end)。

迭代模型iterative model先做出需求的一个简单子集,再扩展或增强,把开发循环重复多次,直到做出完整系统(a simple subset of the requirements is developed, then expanded or enhanced, repeating until the full system has been developed);每一轮都有能运行的部分(working programs are produced for part of the system at every iteration)。

快速应用开发rapid application development (RAD)把需求的不同部分并行开发(different parts of the requirements are developed in parallel),用原型让用户早早参与测试(prototyping provides early user involvement in testing);几乎不做详细计划,尽量复用已有代码(minimal planning; reuses previously written code)。

了解比较三种模型

模型好处代价
瀑布容易管理和理解,每个阶段有明确成果;预算和完成时间更好预测;适合需求已知的小项目后期很难改需求(late changes cannot be accommodated);很晚才有能运行的程序;不适合长而复杂的项目
迭代早期就有能运行的部分;小程序更容易测试和调试(easier to test and debug smaller programs);需求更灵活(more flexible);客户每轮参与,交付时没有意外开头就要把整个系统定义清楚,才能分块;需要良好的整体计划;不适合短而简单的项目
RAD开发时间缩短(reduced overall development time);客户反馈快而频繁(rapid frequent customer feedback);非常灵活;早期就有原型(a prototype is available at an early stage)系统必须模块化(system needs to be modular);需要强大的开发团队;成本和时间难估计(difficult to estimate cost / time);文档常被省略(documentation often omitted)
了解各适合什么项目

瀑布:较小、工期短、需求清楚且不太会变的项目(requirements are well known and unlikely to change)。迭代:主要需求已知,但一些细节会随时间变化(major requirements known but some details likely to change)。RAD:复杂、工期短、业务需求在不断变化的项目(complicated projects developed in a short timeframe to meet the evolving needs of a business)。

了解真题怎么问:哪个团队用哪种模型

"让客户最早参与并得到反馈,小步快跑"是 RAD 或迭代(Rapid Application Development / Iterative):大项目拆成小步,所有用户全程参与,早期就有原型,更容易改需求,计划少,模块可并行开发。"阶段按约定顺序进行"是瀑布(Waterfall):当前阶段成功完成,下一阶段才开始;所有需求在编码前确定;后期变更无法容纳。

12.2结构图

结构图把大问题一层层拆成模块:方框是模块,线是调用关系,箭头表示传递的数据。

结构图structure chart是设计阶段的建模工具,把问题分解成一组子任务(decomposes a problem into a set of sub-tasks),显示各模块的层次结构,以及它们怎样连接和相互作用(the hierarchy of modules and how they connect and interact)。每个模块用一个方框表示(each module is represented by a box),每一层都是上一层的细化(each level is a refinement of the level above)。画完之后,可以据此写出伪代码(derive a pseudocode algorithm)。

常考结构图的符号

图形表示
方框一个模块,过程或函数(module / procedure / function)
方框下的连线上层模块调用下层模块
带圆圈的箭头传递的数据:向下箭头是传给被调用模块的参数(parameter),向上箭头是返回值(return value);BYREF 参数上下各一个箭头(arrows both up and down)
菱形选择:条件为真或假(a condition that could be true or false)
圆弧箭头重复,罩在要重复的几个模块上方(iteration arrow spanning the modules called repeatedly)

了解标识符表写什么

由结构图写伪代码之前,先做标识符表identifier table,列出程序要用的标识符,从结构图的参数可以找出其中的变量。

标识符说明类型
radius存放输入的半径(stores radius input)REAL
answer存放计算结果(stores result of calculation)REAL
pi常量,值为 3.142(constant set to 3.142)常量

评分细则认可的内容:标识符的用途(the purpose of the identifier)、数据类型(the data type)、数组元素个数或字符串长度(the number of elements of an array // the length of a string)、示例值(an example data value)、常量的值(value of any constants used)、作用域(the scope: local or global)。

了解由结构图写伪代码:球的体积和表面积

输入和输出模块写成过程,计算出一个答案的模块写成函数;选择和重复对应菱形和圆弧箭头:

DECLARE radius : REAL
DECLARE answer : REAL
DECLARE reply : STRING
CONSTANT pi ← 3.142

FUNCTION calculateVolume(radius : REAL) RETURNS REAL
    RETURN (4 / 3) * pi * radius * radius * radius
ENDFUNCTION

FUNCTION calculateSurfaceArea(radius : REAL) RETURNS REAL
    RETURN 4 * pi * radius * radius
ENDFUNCTION

PROCEDURE inputRadius
    OUTPUT "Please enter the radius of the sphere"
    INPUT radius
    WHILE radius < 0 DO
        OUTPUT "Please enter a positive number"
        INPUT radius
    ENDWHILE
ENDPROCEDURE

PROCEDURE outputAnswer
    OUTPUT answer
ENDPROCEDURE

CALL inputRadius
WHILE radius <> 0 DO     // 重复:输入 0 结束
    OUTPUT "Volume (V) or Surface Area (S)?"
    INPUT reply
    IF reply = "V"              // 选择:对应菱形
      THEN
        answer ← calculateVolume(radius)
      ELSE
        answer ← calculateSurfaceArea(radius)
    ENDIF
    CALL outputAnswer
    CALL inputRadius
ENDWHILE

12.2状态转换图

状态转换图画的是机器在有限个状态之间怎么变:圆是状态,箭头是转换,箭头上的标签是引起转换的输入。

有限状态机finite state machine是只能处于固定的几个状态之一的机器(can be in one of a fixed set of possible states),外部输入使一个状态变成另一个状态,这叫转换(transition)。状态转换图state-transition diagram画出有限状态机的行为(the behaviour of a finite state machine),说明引起转换的条件,以及转换时做的输出或动作(the conditions needed for a transition, and the outputs or actions carried out)。状态转换表state-transition table列出每个状态、每种可能的输入,以及输入之后的状态(every state, each possible input and the state after the input)。

常考补全状态转换图

图形表示
圆状态(states are represented as nodes)
箭头转换(transitions are interconnecting arrows);回到自己的箭头是循环(loop)
箭头上的标签事件(events are labels on the arrows);有输出时写成「输入 | 输出」,如 A2 | X2(input | output);条件写在方括号里
带黑点的箭头初始状态(the initial state; START → S1)
双圆终止状态(a stopped / final / halting state)

补全时,逐行读状态表,每一行画一条箭头并标好标签;真题还常让你数:转换中有几个会换到不同的状态、有几个带输出(the number of transitions with associated outputs)、终止状态是哪个(the final or halting state)。

12.3三类错误与找错

语法错误让程序跑不起来,逻辑错误让程序跑出错的结果,运行时错误让程序跑到一半出事;IDE 的断点、单步、观察窗口帮你找到出错的那一行。

语法错误syntax error是源程序在语法上的错误(errors in the grammar of a source program),违反了语言的规则(the rules of the language have been broken),编译或解释时就会检查出来,改正之前程序不能执行。逻辑错误logic error是程序逻辑上的错误(the program does not do what it is supposed to do),程序能运行,但结果不对,通常在测试时发现。运行时错误run-time error在程序执行时才出现,程序可能意外停止(the program may halt unexpectedly),或者陷入死循环,只能强行停止(go into an infinite loop)。

了解区分三类错误

错误什么时候发现程序能不能运行
语法错误编译或解释时(syntax is checked when compiled or interpreted)不能,改正前不能执行
逻辑错误测试时,结果和预期不符能运行,但结果不对
运行时错误程序执行时运行到出错处意外停止,或死循环

了解用 IDE 工具找错:先断点,再单步,看观察窗口

断点breakpoint: stops the code executing at a set line
→
单步执行single stepping: run the code one line at a time
→
观察窗口watch window: displays the value of variables

断点breakpoint设在出问题的函数开头,让程序在那一行停下(stops the code executing at a set line);然后单步执行single stepping,一次执行一行(execute one statement / instruction at a time);同时在观察窗口watch window里看变量的值(displaying the value of variable(s); also called report window)。回答"解释这几个功能和使用顺序"时,要以断点开头。

了解编写代码时 IDE 怎么帮忙

自动补全或自动更正(auto-complete / auto correction);识别未声明的变量(identify undeclared variables);美化打印、自动缩进、高亮结构(pretty print / auto-indentation / structure highlighter);动态语法检查,给不符合语言规则的语句加下划线或高亮(dynamic syntax checking: underlines or highlights statements that do not meet the rules of the language);折叠和展开代码块(expand / collapse code blocks);根据上下文提示(context-sensitive prompts)。

了解怎样少出错,测试能做到什么

多数错误出在设计上。分析结束时写出全面严格的规格说明,设计时用结构图、状态转换图和伪代码(structure charts, state-transition diagrams and pseudocode),编码时用信息隐藏、封装和异常处理,都能避免错误。测试能暴露错误,但不能保证大而复杂的程序在任何情况下都没有错(testing will show the presence of faults, but cannot guarantee that large, complex programs are fault free)。程序已发布后出现运行时错误,开发者可以发一个补丁(patch: a small program released by the developers to correct an error or provide extra functionality)。

12.3人工试运行与走查

伪代码写完先不运行:手工一行一行执行,把变量的变化记在跟踪表里,编码之前就能找到错误。

人工试运行dry run是手工把程序或模块从头执行一遍(working through a program or module from a program manually),结果记在跟踪表trace table里:每个变量一列,随着变量变化逐行记录(columns showing the value of each variable as it changes)。走查walkthrough是人工试运行的正式版本,用事先定好的测试用例(a formal version of a dry run using pre-defined test cases):由团队里的另一个成员独立执行,或者开发者带着大家过一遍。

了解做跟踪表的步骤

变量和输出各一列a column for each variable and the output
→
一组测试数据写一行pre-defined test data
→
逐行执行,变量变了就写新值work through the code line by line
→
和预期对比,找出错误,改后重做expected result vs actual result

了解走查之前要准备什么

要有程序的代码或规格说明(the program / source code / specification),以及测试计划:输入的测试数据和预期输出(test plan // inputs / test data and expected outputs)。原因:必须知道程序的结构、设计或算法(the structure / design / algorithm of the program needs to be known),才能测试经过程序的所有路径(so that all paths through the program can be tested)。

12.3测试计划与测试数据

先定测试策略,再列测试计划:测什么、用什么数据、预期什么结果;测试数据分正常、异常、极端、边界四类。

测试策略test strategy在分析阶段定下,是对整个测试的概述,说明怎样测、什么时候测(an overview of the testing required; how and when the program is to be tested)。测试计划test plan是详细的清单,列出所有测试阶段和每一项测试(a detailed list showing all the stages of testing and every test that will be performed),常做成表:测试、目的、测试数据、预期结果、实际结果(test / purpose / test data / expected outcome / actual outcome)。测完把实际结果填进去,和预期不符就改正,再测一遍。

正常数据normal test data应该被程序接受(should be accepted by a program)。异常数据abnormal test data应该被程序拒绝(should be rejected by a program),比如类型不对的数据。极端数据extreme test data正好在程序接受范围的极限上(on the limit of that accepted by a program)。边界数据boundary test data是极限上的数据,或者刚好在极限之外、应被拒绝的数据(on the limit accepted, or just outside the limit that is rejected)。

常考设计测试数据、填测试计划

FUNCTION InRange(Value : INTEGER) RETURNS BOOLEAN
    IF Value >= 24 AND Value <= 37
      THEN
        RETURN TRUE
      ELSE
        RETURN FALSE

12.3从模块到整体的测试

先测单个模块(白盒看内部路径,黑盒看输入输出),再拼起来测(集成,没写好的用桩);整个程序完成后依次做阿尔法、贝塔、验收测试。

白盒测试white-box testing测每个过程内部是怎么工作的,走遍模块里的每条路径(the structure and logic of every path through a program module);黑盒测试black-box testing只测模块的输入和输出(a module's inputs and outputs),不管内部结构。集成测试integration testing测分别写好的模块能否一起工作(modules that have already been tested individually are combined and tested as a whole);其中有模块还没写,就用假模块代替,这是桩测试stub testing(dummy modules used for testing purposes)。

程序完成后整体测试,依次是:阿尔法测试alpha testing,开发团队在内部测试快要完成或已完成的程序(in-house by the development team);贝塔测试beta testing,一小组用户在程序正式发布之前试用(a small group of users before it is generally released);验收测试acceptance testing,向客户证明程序在实际使用环境中达到要求(prove to the customer that it works as required in the environment in which it will be used)。

常考判断是哪种测试

题目里的线索答案
各队写好的模块合在一起测集成测试(integration testing)
有的模块还没写,用假模块顶上桩测试(stub testing)
开发团队在公司内部测试阿尔法测试(alpha testing: carried out in-house)
先在一两家店或一小组用户里试用贝塔测试(beta testing)
客户在自己的硬件上确认,最后一步验收测试(acceptance testing)
只看输入和输出,不看内部黑盒测试(black-box testing)
走遍每一条路径白盒测试(white-box testing)

真题的叙述顺序也是这个顺序:分析、设计、编码,各模块集成测试,阿尔法,贝塔,验收,上线后遇到问题进入维护。

12.3程序维护

程序不会磨损,但会遇到没想到的情况和新要求:改错是纠错性,提高性能是完善性,增加新功能是适应性。

程序投入使用后,可能出现逻辑错误或运行时错误,用户也可能想换一种方式使用,所以要维护。纠错性维护corrective maintenance改正使用中出现的错误(the correction of any errors that appear during use);完善性维护perfective maintenance改进程序使用中的性能(improvements to the performance of a program);适应性维护adaptive maintenance改动程序,让它完成新的任务(the alteration of a program to perform new tasks)。

常考判断维护类型

题目里的线索答案
上线第一周报告了意外的错误纠错性(unexpected bugs are reported: CORRECTIVE)
为提高响应速度而修改完善性(improve the speed of response: perfective)
客户还要原来没约定的功能适应性(extra features which were not originally agreed: ADAPTIVE)
要支持新的操作方式,如语音命令适应性(new tasks required by the customer)

需要适应性维护的原因:需求变了(change to requirements);有了新技术,或用到的库模块改了(new technologies available / changes made to library modules);相关法律变了(change in relevant legislation)。
